# MaatLog profile

`profile=maatlog`（省略時の既定）に適用する。
RST 構造と4段階 lint は [共通 guide](../rst-core-style-guide.md)、入力と root 解決は [入力仕様](../profile-interface.md) を読む。

## 言語と文書構造

既定は日本語・である調。明示された `language` を優先し、英語などの本文に日本語の文体・句読点を押し付けない。
日本語の文書はタイトル直後の「概要」で目的を1〜3文で述べ、最終行に装飾なしで単独の「以上」を置く。
他言語ではこの役割に相当する見出しと終端を指定言語で書く（英語なら `Overview` と `End`）。
「本ドキュメントでは」などの自明な説明を避ける。

[文書種別表](../document-types.md) から template を選ぶ。
procedure は前提条件・手順の流れ・手順・結果確認、explanation は概念・構造・比較・関連資料を軸にする。
operational は procedure の簡易版で、前提条件と手順の流れを省略できる。
template の欄は必要な内容で置き換える。参照先の節には一意なラベルを付け、無関係な節や未確認の関連 URL を埋め草として残さない。
既存編集は指定箇所の追記・修正を優先し、template で文書全体を置換しない。

## 日本語のテキスト

- 一文の読点「、」は最大3つ。地の文だけを数え、コード・リテラル・図・list-table セル内は除く。
- 4つ以上の読点で語句を列挙しそうなら箇条書き、説明付きの列挙ならフィールドリストにする。
  節の接続で増える場合は複数文に分ける。
- 句点「。」の直後で改行する。桁数を理由に文の途中を折り返さない。
- テキストブロックの最後の文では句点を省く。単独の文、空行・リスト・コード・節の前も同じである。
- コロンは半角にする。RST 構文で必要な場合を除き行末をコロンで終えない。

```rst
対象を確認する。
次の項目を記録する

- 担当者
- 時刻
- 対象
- 件数
- 失敗理由
```

フィールドリストの継続行やブロックの字下げは共通 guide に従う。

## コマンドとコード

標準シェルは zsh。bash はツールのインストールや bash スクリプトの実行など、必要な場面に限る。
明示された場合以外は GUI の手順を追加しない。
コマンドの前には実行の意図を動詞で説明し、「以下のコマンドを実行する」や体言止めを避ける。
コマンドはできるだけ1行で記述する。

Python だけ `.. code-block:: python` を使う。zsh / bash / json / yaml を含むそれ以外のコードは従来どおり `::` を使う。
コードは4スペース字下げする（リスト内では項目本文から4スペース）。

```rst
待機中の処理を表示する ::

    printf '%s\n' queue

.. code-block:: python

    print("queue")
```

## 図

Sphinx 拡張は sphinx-oceanid、directive は `.. mermaid::` を使う。`.. oceanid::` は使わない。
directive の前後に空行を置き、図の本文は4スペース字下げする。
この profile で使う図は従来の6種類に限る。

| 図 | 構文 | 用途 |
|---|---|---|
| Flowchart | `flowchart TD` / `graph TD`（向きは TD / LR） | 構成・依存・処理の流れ |
| Sequence Diagram | `sequenceDiagram` | 時系列の通信 |
| State Diagram | `stateDiagram-v2` | 状態遷移 |
| Entity-Relationship | `erDiagram` | データや資源の関係 |
| Class Diagram | `classDiagram` | 階層・分類 |
| XY Chart | `xychart-beta` | 数値の比較・推移。beta の表現範囲に留める |

Gantt、Pie、Mindmap、Timeline、Sankey 等を追加しない。

```rst
.. mermaid::

    flowchart TD
        A[処理を確認する] --> B[失敗した処理を待機させる]
        B --> C[再実行する]
```

## 専門用語と用語集

用語集の正本は、入力仕様で確認した **`APP_ROOT/docs/glossary.rst`** である。
新規 draft の既定先 `ENV_ROOT/docs_draft/` と混同しない。親 `docs/glossary.rst` は読まず、新設・編集しない。

ドメイン固有の略語、プロダクト・アーキテクチャ固有の語、説明なしでは通じない IT 専門用語を扱う。
IP アドレス・ネットワーク・サーバ等の一般的な語、その場で説明し終えた自明な語は対象外とする。
判断に迷う場合は `audience` を踏まえ、読者が定義を用語集で引く必要があるかで決める。
本文で用語として採用した語は、初出だけでなく地の文の **全出現** を `:term:` でマークする。

```rst
:term:`キュー` を確認する。
失敗した処理は :term:`遅延再試行` で再実行する
```

表示名とキーを変える場合は `` :term:`表示名 <用語>` `` を使う。
role の前後は共通 guide の境界スペースに従う。
コードブロック、リテラル（インラインを含む）、Mermaid 図、見出しの中には term を入れない。
list-table のセル内は term を使ってよいが必須ではない。

### 追記する範囲と別名

1. 本文に実際にマークした語を列挙し、既存 glossary の用語と別名を照合する。
2. 既存の語・別名は追記せず、本文の全出現のマークだけを整える。
3. 今回本文で使った未定義語だけ、既存の `.. glossary::` 配下へ追記する。
   本文に出てこない語や他の文書の語を先回りで追加しない。
4. 略語と正式名など複数の表記を本文に使った場合は、同じ定義の別名行として並べる。
   定義済みの別名を新しいエントリとして重複させない。

用語集の更新は指定 target 以外を編集できる既存の例外である。
新しい glossary directive、別の用語集、`:orphan:`、toctree 登録を追加しない。
全ての term に解決先をそろえ、将来のビルド時の未定義語 warning を防ぐ。

### 定義の書き方

既存 directive の字下げに揃えて用語・別名を並べ、その行からさらに4スペース字下げして定義を書く。
日本語の定義はである調・句点改行・ブロック末尾句点省略とし、文の途中を折り返さない。
おおむね2〜6行を目安に、意味が自己完結する粒度で簡潔に説明する。

```rst
.. glossary::

    キュー
    queue
        処理を順番に保持する仕組みである。
        待機中の処理を取り出す順序を管理する
```

上記は既存 directive 内のエントリ形式の例であり、directive を新設する指示ではない。
定義中で関連語を term 参照する場合は、既存語または今回の本文で採用した語に解決させる。
定義のためだけの未定義語を連鎖して増やさない。

## 検査

`LINT_PROJECT` は選択した `APP_ROOT` の公開 Python project とする。
対象は今回作成・編集した RST の絶対パス。用語集も編集したときだけその絶対パスを加える。
親 cwd でも `uv run --project "$APP_ROOT" ...` 相当で公開 project を選び、共通 guide の4検査を指定順・指定フラグで実行する。
親の `.venv` や `tools/devenv` を検査 project の代わりに使わない。

MaatLog の通常執筆では Sphinx build（`make html`）は不要である。
この方針は MaatLog に限り、他 profile の build 方針を省略する根拠にはしない。
