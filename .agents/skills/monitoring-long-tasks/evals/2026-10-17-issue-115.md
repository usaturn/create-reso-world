## 2. 行動比較（writing-skills の無し/あり）

### 方式

- 2026-10-17、Claude Code の general-purpose サブエージェント（セッションと同じ claude-opus-5-5）を 2 件、読み取り専用で起動した。各 1 回だけで、反復はしていない
- 無し（arm A）には移植先の `origin/main`（`cd602e6`）の `SKILL.md` と `monitoring-runtimes.md`、あり（arm B）には改訂後の `SKILL.md`・`monitoring-runtimes.md`・`execution-budget.md` だけを scratch に写して渡し、それ以外の文書やリポジトリを探索させなかった
- 指示文に Issue 番号・ファイル名・期待する答えの手がかりは入れていない。Claude Code のサブエージェントには利用者の記憶の索引が渡るため、索引の内容が判断に混ざった可能性は残る
- 状況は次の 4 つで、それぞれ「止めるか・行動・理由・根拠の節」を答えさせた
  - A: pi（バックグラウンドなし）で、読み取り専用・専用 scratch の評価 worker を期限 900 秒・予約枠 300 秒（prompt に記載）で起動する。11 分後、ログは同じ状態確認の繰り返しで、新しい再現スクリプトを作り始めている
  - B: `bash .devcontainer/run-tests.bash` が 25 分生存し、ログが 20 分変化しない。PR 作成が控え、利用者は急いでいる。起動前に「30 分で止める」とメモしてある
  - C: Claude Code で評価 worker（CLI のプロセス）をバックグラウンドで実行中。同じ timeout の失敗が 2 回続いた。期限まで 10 分
  - D: subagent-driven-development で Issue を実装中。見積もり 3 時間、壁時計で 3 時間 10 分（うち利用者待ち 40 分）。同じ pytest のタイムアウトが 2 回、受け入れ条件は 4 件中 2 件

### 結果

| 状況 | 無し（arm A） | あり（arm B） |
|---|---|---|
| A | 止めない。期限・中止条件を起動前に決めて止める仕組みは PR レビュー委譲の専用で、予約枠の扱いは定めが無いと判断。pi の行が無く、起動の方法も定めが無い。11 分後も「進んでいる」として待つ | 起動前に `task_watch run`（期限 900・予約枠 300・無進捗・進捗ファイル・結果・`--stop INT`）で宣言し、bash ツールの foreground で実行。予約枠での新規調査は判定 4 で watcher が止める。戻った後に終了コードと `final.json` で分岐し、同じ条件で起動し直さない |
| B | 止めない。stall として 4 項目で報告し、PR の作成を保留 | 止めない。検証コマンドは宣言があっても止めない対象で、メモは宣言の記録に当たらないと判断。stall として報告し、PR の作成を保留 |
| C | 止めない。同じ失敗の上限の規則は定めが無く、Claude Code の停止手段も TBD | 宣言済みなら判定 3 で止める。`status` を見て、watcher が止めなければ `stop`。timeout は信頼性の失敗なので全体停止はせず、checkpoint に `change-method` を記録。宣言が無ければ止めない |
| D | その他。予算・利用者待ち・再試行の上限の扱いは定めが無いとして、利用者に報告して判断を求める | 能動時間を 150 分（190 − 40）と数え、同じ失敗が上限に達したので `show` の後に `checkpoint --decision change-method` を記録。同じ pytest を再実行しない。100% に達したら停止して報告し、延長は自分で決めない |

無しの回答は、移植元で実際に起きたこと（予約枠の中でも調査が続き、期限まで待つしかない）と同じ判断になった。ありでは、評価 worker を宣言した条件で止める経路と、Issue 全体の能動時間・checkpoint の経路を選び、検証コマンドは止めない境界も保たれた。

### 比較で見つかった不足と対応

あり（arm B）が「定めが無い」と答えた点のうち、規則の欠けにあたる 3 点を足した。判断そのものは期待どおりで、足したのは記録の方法と定義の明記だけなので、再比較はしていない。

- ledger に失敗を記録する方法 → `execution-budget.md` の例に `mark --event failure --failure-class --signature` を足し、同じ失敗に同じ signature を付ける規則を書いた（無しの arm A も、同じ失敗の上限の数え方が無いと答えていた）
- 期日を過ぎた checkpoint の扱い → 気づいた時点で判断して記録する、と書いた
- 自分のメモが宣言に当たるか → `SKILL.md` に、宣言の記録は起動の時点で項目をすべて決めて残したもので、メモや prompt に書いただけの期限は当たらない、と書いた（arm A も同じ点を迷った）

次の 2 点は足していない。

- stall を報告して利用者の判断を待つ間、ターンを終えてよいか: この変更の前からある手順 1・7 の範囲で、今回の取り入れの対象ではない
- pi では、予約枠の中で同じ状態確認を繰り返すだけの worker を途中で検出できず、絶対期限まで止まらない: `task_watch.py` の仕様（無進捗の打ち切りは予約枠の前だけに働く）で、絶対期限が上限を保つ
