# 要件・原因・検証を対応させる

既存の Spec・Plan・経路表・ledger に以下を記す。単純な変更は短い対応メモでよく、別帳票や全組み合わせの網羅は求めない。指摘の採否、自己レビュー上限、権限・公開範囲は呼出元のスキルに従う。この資料はそれらを広げない。

## 1. 実装前の要件照合

初回実装では、Spec の約束する条件と除外範囲を読み、条件ごとに「担当 Task／観測する結果／検証方法」を Plan と照合する。Task の足し合わせで条件が満たされるか、Plan が要件を落とす・保証を狭める形になっていないかを確認してから実装へ進む。

レビュー修正では、採否の分類後、経路表の作成・修正方針の決定より前に、PR の約束・制限と既存 Spec・Plan を読む。条件ごとに「今回の修正方針／観測する結果／検証方法」を対応付け、既存 Spec の短い対応メモにする。最初は修正・検証の予定を記し、後続の経路表と方針へ反映する。既存 Spec・Plan が無ければ PR と依頼を基準にし、その不在も記す。存在しない文書や承認を補わず、対応メモは呼出元の手順で書く Spec へ引き継ぐ。

いずれも、不一致は元の要件を満たす形で直す。要件自体の変更が必要なら、既存の承認・委任範囲を確認し、範囲外の変更を独断で確定しない。

別担当・別ファイルでも、同じ入力の解釈、状態の読取・書込、操作順、外部仕様に依存する箇所を探す。共有する条件の確認を、初回実装では統合担当の Task に、レビュー修正では要件対応と経路表の統合担当に割り当て、担当名または役割と検証方法を記す。共有条件が無ければその旨を短く書く。各担当へは該当条件・除外範囲・共有前提・必要な証拠を渡し、ファイル単位のテスト成功だけを全体の保証へ読み替えない。

## 2. 原因から影響経路を作る

指摘された行・関数名だけでなく、「どの前提が、どの境界・操作順で破れたか」を原因の単位として1文で書く。同じ条件を利用する入口、変換、読取・書込、副作用、終了・復旧まで因果関係を追い、既存の経路表を作る。差分外の関連経路も含めるが、原因の異なる新規欠陥探しへ広げない。

各経路を次のように扱う。

| 判定 | 計画時に記すこと | 完了の根拠 |
|---|---|---|
| 修正する | 変更内容、観測する結果、確かめる方法 | 修正後の対象版で観測した結果・実行証拠 |
| 既に満たす | 条件が成り立つ根拠、観測する結果、確かめる方法 | 対象版で条件を確かめた結果・証拠 |
| 対象外 | その原因と関係しない、または保証の対象でない理由 | 理由と既存の要件・除外範囲との一致 |

証拠はコマンド・入力・観測結果・対象の HEAD または差分・ログや該当箇所を結び付ける。文書だけの変更では構造・参照・シナリオの判断記録で代える。方法の予定、テスト名の一覧、チャットでの注意共有、修正済みとの申告は実行証拠ではない。未実施・未確認の行はその状態のまま残し、「既に満たす」「完了」にしない。

後続の指摘は現行版で確認し、以前の原因・修正履歴と比較して次の4種類に分ける。これは指摘の採否の分類とは別軸であり、自動で採用・除外する規則ではない。

- **既存原因の適用漏れ**: 同じ条件が別の経路で未解消。既存の原因・経路表へ戻し、同系・別IDというだけで重複として捨てない。
- **修正による回帰**: 修正前後の対照や履歴で因果関係を確認し、影響する経路と証拠を更新する。
- **別の原因**: 独立した前提の破れ。既存スキルの採否基準で判断する。
- **新しい要求**: 既存の約束・除外範囲では求めていない保証。既存の委任・承認範囲で判断し、修正の名で無断追加しない。

未確認なら分類も仮置きとし、確認してから確定する。既存の再発時の設計見直しのきっかけは、そのまま適用する。

## 3. 検証と閉じ方

判定を変えたら、拒否すべき入力と引き続き受け入れるべき入力を対にする。順序に意味がある処理は、前後の操作、中断、復旧、失敗後の次操作も、その条件が影響する範囲で確かめる。片側だけの成功では経路を閉じない。

fixture・fake・期待値が実装と同じ仮定・変換から作られていないか確かめる。共有しているなら、外部仕様、独立に構成した入力と期待結果、変更前後の対照など、対象に合う根拠を選んで記録する。テスト件数・移植元の実績はその代わりにならない。独立した根拠が得られないときは保証を確定しない。既存の安全ガードの対照検証は維持するが、全コードの変異テスト、有料実機の反復、文書の固定文言テストを追加の必須条件にしない。

最後の修正で影響した経路は、観測結果と証拠を対象版に更新してから公開する。影響しない証拠を引き継ぐときも、変更がその前提を変えない理由を書く。古い HEAD の成功や別版のレビューを、変更した経路の現行版の保証へ流用しない。

統合担当は要件対応と経路表を照合し、修正する・既に満たす各行に必要な証拠があること、対象外の理由が保証と矛盾しないことを確認する。finding の修正件数ではなく、原因に関わる必要な経路と証拠が揃ったかで完了を判断する。自己レビュー上限に達しても未確認が解消するわけではない。上限後は再レビューせず、既存手順の修正・検証・記録を行う。
