## 1. 目的

利用者は、`review-fix-planning` を使う代わりに次の指示を渡すと、おおむね良い結果になることを確かめた。この指示の内容を `review-fix-planning` に取り入れ、スキルを呼ぶだけで同じ結果になるようにする。

```text
PR ${PR_URL} とレビュー結果 ${REVIEW_PATH} を確認し、修正要否を確定してください。
最終結果は次の三択です。

1. 修正が必要：推奨案を基本に修正し、検証・PR全体の再レビューを完了してプッシュする。
2. 修正が不要：必要な確認・検証を完了し、最終ステータスコメントを投稿してマージし、関連Issueを更新する。
3. 権限・環境・外部障害などで自力で継続できない場合だけ、未完了であることと具体的な停止理由を報告してください。

作業条件：
- pr-reviewは使わず、専用worktreeで作業する。
- 修正要否にかかわらず、全指摘、変更ファイル全文、関連処理・テストを確認する。
- 同じ原因の関連箇所はPR差分外も修正する。
- 利用可能なサブエージェントに独立した調査・検証を委譲し、使えなければ自分で行う。
- 致命的な指摘のみ修正する
- 修正する場合は、後続のレビュー、修正で手戻りを発生させないことに注力せよ。これは自身で何度もレビューと修正を繰り返して良いという意味ではない（修正後の自己レビューは最高でも1回とする）
- 修正後の自己レビューは最高でも1回とするが、この1回には複数のサブエージェントに別の視点で、それぞれ同時にレビューさせることを1回として数えて良い

確認不足・未読・未検証は途中状態であり、第三の終了結果ではありません。
自分で解消し、「追加確認が必要」を結論として終了したり、確認作業をユーザーへ返したりしないでください。
未確認を「修正不要」と扱わず、上記の完了条件を満たした場合だけ完了を報告してください。
```

あわせて、Issue #5 の対応方針 A のうち、この指示と同じ方向の項目（重大度による判断、同じ原因の横展開、ループの停止基準）と、Issue のコメントの改善案の要点（P1 の影響経路の表、P4 の反証を担当するレビュー）を取り入れる。

## 2. 背景

### 2.1 Issue #5 が指摘した原因（スキル側）

- 採用基準 (a)「現行 HEAD で再現した誤動作」に重大度や起きやすさの足切りが無く、Low でも直していた
- 「レビューに挙がっていない問題を新たに探しに行かない」規則のため、修正が再現した 1 経路に限られ、同じ原因の隣の経路が次のレビューで見つかっていた（usaturn/resoloop#5、PR #16 の 3 経路、PR #27 の事前検査）
- `Approve` と「直すものが無い」が一致せず、ループ全体の終了条件が無かった

### 2.2 指示を使った実例

- PR #33（Issue #22 の統合）では、この指示の前半（三択、差分外の同じ原因、確認作業をユーザへ返さない）を事前に渡して進めた。ただし「致命的な指摘のみ」と「自己レビューは 1 回まで」が無かったため、事実として正しい Info 指摘をすべて直し、PR 全体の再レビューを 9 回繰り返した。9 回目の途中で利用者が「致命的な問題が起きるかどうかで判定せよ」と指示し、そこで収束した（`docs/superpowers/specs/2026-10-05-pr33-issue-22-integration-review-fixes-design.md`）
- PR #35 は、修正不要と判定してマージした
- 今回の指示は、この 2 つの規則を加えた版である

## 3. 決定事項

### D-1 依頼の種類で流れを選ぶ

| 依頼 | 流れ |
| --- | --- |
| 計画で止めることを明示した依頼（「計画だけ」「承認を待って」「実装しないで」「Spec を見せて」など） | 計画のみ。従来どおり Spec → 確認用コピー → 承認を得て停止。承認後は「実装後」 |
| 承認済み Spec の実装・反映だけの依頼 | 従来どおり「実装後」の手順だけ |
| それ以外のすべて（「修正要否を確定して」「指摘に対応して」「修正計画をたてて」を含む） | 三択の完遂（既定） |

「修正計画をたてて」とだけ頼まれた場合も、計画で止めることを明示していないので完遂になる（設計の承認時に確認済み）。

### D-2 結論は三択に限る

1. **修正が必要**: 推奨案を基本に修正し、検証と自己レビューを経て push する
2. **修正が不要**: 必要な確認・検証を完了し、最終の状況コメントを投稿してマージし、関連 Issue を更新する
3. **停止**: 権限・環境・外部障害で自力では続けられない場合だけ。未完了であることと具体的な停止理由を報告する

確認不足・未読・未検証は途中の状態であり、結論ではない。自分で解消する。「追加確認が必要」を結論にしない。確認作業をユーザへ返さない。未確認の指摘を「修正不要」として扱わない。この規則は、言い訳と実態の表と Red flags に入れる。

### D-3 完遂の依頼を実装修正の実行許可として扱う

完遂の依頼は、その PR の実装修正（approved PR review-fix implementation）と、結論 2 のマージ・Issue 更新の実行許可を含むものとして扱う。`AGENTS.md` の「リポジトリ境界」の表と `docs/superpowers/README.md` は「承認済み実装修正」の経路を維持すると書いており、この扱いで両方を変えずに済む。一般的な外部実装・Issue 実装への許可は広げない。

### D-4 専用の worktree で作業する

- `pr-review` スキルは使わない。修正後の自己レビューもこのスキルの中で行う（D-10）
- PR の head ブランチを checkout した専用の worktree を作り、修正・Spec のコミット・push をそこで行う。置き場所は、対象リポジトリにかかわらず `PARENT_ROOT` の `.worktrees/<owner>-<repo>-pr<N>-review-fix`（create-reso-world の `.gitignore` が `/.worktrees/` を除外している）
- head のコミットは、`PR_REMOTE` から `pull/<N>/head` を fetch して得る。fork からの PR でも同じ手順で取れる。取得した SHA が `gh pr view --json headRefOid` と一致することを確かめる
- ローカルに head ブランチが無ければ、その SHA から作る。ある場合は、その先端が PR の head と同じか、その祖先（fast-forward できる）のときだけ使う。PR に無いコミットを持っていれば、誰かの未 push の作業なので、触らずに結論 3 にする
- head ブランチが別の worktree で checkout されているときは、その worktree に未コミットの変更が無く、HEAD が PR の head と同じなら、それを専用の worktree として使う。片付けの対象にはしない。それ以外は触らずに結論 3 にする
- 専用の worktree を `CODE_ROOT` にして、共通 context の確認を `HEAD_REPO`・`HEAD_BRANCH` 付きで再実行する。既存の helper は、修正用の worktree が同じ Git repository に属することと、ブランチが head と一致することを確かめる
- 作業が終わったら（結論 1 の push 後、結論 2 のマージ後、結論 3 の停止時のうち未コミットの変更が無いとき）、このセッションが作った worktree を外す。このセッションが作ったローカルブランチは、リモートの head と同じ SHA であることを確かめてから削除する

### D-5 確認の範囲と、サブエージェントへの委譲

- 結論にかかわらず、全指摘、PR の変更ファイルの全文、関連する処理とテストを確認する
- 専用の worktree に変更が無く、HEAD が PR の head と一致している間は、その中のファイルを committed content として読んでよい。挙動の再現で一時的なコードを書くときは、従来どおり `mktemp` の隔離 worktree を使い、専用の worktree を汚さない
- 指摘ごとの検証・再現と、関連箇所の調査は、互いに独立していれば、使えるサブエージェントに任せる。使えなければ自分で行う。サブエージェントの完了・生存の監視は `monitoring-long-tasks` スキルに従う
- 確認中に、PR が持ち込んだ致命的な欠陥を自分で見つけた場合は、指摘と同じように扱う（出どころは「自己確認」）。PR と関係しない既存の問題は直さず、致命的なものだけ報告に書く

### D-6 分類は 3 区分、「対応する」は致命的なものだけ

- 区分は「解消済み」「対応する」「対応しない」の 3 つにする。**「判断保留」は廃止する**。完遂ではユーザに選ばせる段が無く、計画のみの流れでは利用者が Spec を見て覆せるため
- 「対応する」に入れるのは、次の両方を満たすもの
  - **致命的である**: 直さずにマージ・利用すると、実在する構成やサポートしている使い方で、次のどれかが起こり得る
    - 秘密情報の露出
    - データの消失・破損
    - 了承の無い設定変更、誤った対象（リポジトリ・ファイル・共有先）への操作
    - 手順・ツールのとおりに使うと誤った結果になる、主要な処理や CI が止まる
    - セキュリティ上の問題
  - **現行 HEAD で確認できた**: 従来の (a) 再現した誤動作、(b) 事実誤認の記述（そのとおりに進めると誤った結果になるもの）、(c) 理由なく削除された回帰ガード
- ユーザが名指しで依頼した指摘（従来の (d)）は、致命的でなくても対応する
- レビューの重大度ラベル、何モデルが指摘したか、`Approve` かどうかでは決めない。起こり得るかどうかは、発生条件が実在する構成・使い方で到達できるかで判断し、その条件を 1 行で書く
- 「対応しない」の典型に、事実として正しいだけの指摘（記録の書き方、列挙の漏れ、表記の揺れ、網羅の粗さ）を加える。従来の典型（仕様・設計の是非、第三者互換、将来の保険、性能の過剰近似）は残す
- この分類は、計画のみの流れと、自己レビューで出た指摘にも同じく使う

### D-7 守る条件と影響経路を列挙してから直す

「対応する」項目ごとに、修正の前に次を書く（Issue #5 の A-2 と、コメントの P1 の要点）。

1. 破れている条件（守るべき性質）を 1 文で書く
2. 同じ条件に頼っている経路を、PR の差分外も含めて列挙する。変更する関数や helper の呼出元、同じ判定をする別の分岐、同じ前提を持つ別ファイル、変更前の挙動を保つ必要のある呼出元を含める
3. 経路ごとに「修正する」「既に満たす（根拠）」「対象外（理由）」を決め、「修正する」と「既に満たす」の行には確かめる方法（テスト・コマンド・再現手順）を付ける

この表を Spec に残し、自己レビュー（D-10）の入力にする。列挙は、条件に頼る経路を確かめる作業であり、原因の異なる新しい問題を探す作業ではない。

### D-8 対応しない実在の制約を PR の説明とそろえる

「対応しない」とした指摘のうち、実在する制約（直さないが事実として起こるもの）が PR の説明の保証と食い違う場合は、PR の説明の既知の制限に、その条件と回避方法を書き足す（Issue #5 のコメント 2 の 7.4）。同じ論点が次のレビューで繰り返し挙がるのを防ぐため。

### D-9 結論 1 の手順

1. 推奨案を基本に修正する。設計の選択が要る場合も、推奨案を選んで理由と他の案を Spec に残す（ユーザに問わない）。D-7 の表の「修正する」の行は、PR の差分外も同じ PR で直す
2. 「実装後」の検証（実装に関連したテストと、変更の種類に応じた検証）を通す。失敗したら直す。base でも同じように失敗する既存のテストは、base での結果を根拠として記録し、先へ進めてよい
3. 自己レビューを 1 回だけ行う（D-10）
4. 自己レビューで出た致命的な指摘を直し、手順 2 の検証をやり直す。2 回目のレビューはしない。致命的でない指摘は「対応しない」として記録する
5. Spec に結果を書いてコミットする（D-14）
6. 「実装後」の手順 4〜5 のとおり、既存 PR の head へ push する。その後、状況コメントを投稿し（D-15）、専用の worktree を片付ける（D-4）

### D-10 自己レビューは 1 回、観点を分けて同時に

- 修正後の自己レビューは最大 1 回とする。使えるサブエージェントが複数あれば、別々の観点を同時に担当させ、それを 1 回と数える。使えなければ、自分で全観点を 1 回だけ見る
- 観点は次の 3 つとする
  1. **反証**: D-7 の表を渡し、修正した条件が破れる入力・操作順・経路と、旧版との挙動の差を探す
  2. **PR 全体**: 修正後の PR の全差分と変更ファイルの全文を読み、致命的な問題を探す
  3. **検証の検出力**: 追加・変更したテストと検証が、修正対象の欠陥を実際に検出できるか（assertion が変更対象全体を見ているか、別の拒否理由に隠れていないか）
- レビュー担当には、守る条件・影響経路・実行した検証・未確認の事項を渡す。指摘には、再現手順か根拠（ファイルと行）を付けさせる
- 指摘は D-6 で判定する。指摘 0 件を、未確認の事項が解消した証拠として扱わない

### D-11 結論 2 の手順

1. PR の変更の種類に応じた検証を、専用の worktree（PR の head）で通す
2. base が PR の分岐点より先に進んでいる場合は、push しない一時的な統合ツリー（`mktemp` の隔離 worktree で、head に base を merge したもの）でも同じ検証を通す
3. base と競合してマージできない場合は、競合の解消を修正として扱い、結論 1 に切り替える
4. `AGENTS.md` の「GitHub Actions」の規定で CI を確認する対象のリポジトリなら、PR のすべての check の成功を確かめる。PR の変更が原因の失敗は致命的な指摘として結論 1 に切り替え、基盤の障害なら結論 3 にする
5. Spec に結果を書いてコミットする。PR が create-reso-world のものなら、Spec は PR の head に載るので、push してから先に進む（D-14）
6. 最終の状況コメントを投稿する（D-15）
7. `gh pr merge "$PR_NUMBER" --repo "$PR_REPO" --merge --match-head-commit "$HEAD_SHA"` でマージする。`HEAD_SHA` は検証した（Spec を載せた場合はその push 後の）head である
8. 関連 Issue を更新する
   - `closingIssuesReferences` の Issue: マージ後に自動で close されていなければ、結果をコメントして close する
   - PR の本文・タイトルで参照しているだけの Issue: マージの結果と残りの作業をコメントする。本文のチェック項目のうち、この PR で完了したことが明らかなものは、本文を取り直してから `[x]` にする
9. 専用の worktree を片付ける（D-4）

### D-12 マージしてよい範囲

マージするのは `usaturn/create-reso-world` と `usaturn/resoloop` の PR だけとする。それ以外（上流の `orange3134/resoloop` など）、draft の PR、close・マージ済みの PR は、修正不要と判定してもマージせず、結論 3 として停止理由を報告する。範囲外のリポジトリへのコメント投稿は、従来どおり commit / push まで行ったターンだけ必須とする。

### D-13 結論 3 の対象

次の場合だけ結論 3 にする。

- 権限: マージしてよい範囲外のリポジトリ、push・マージの権限が無い、`gh` の認証が無い
- PR の状態: draft、close 済み、マージ済み
- 環境: 共通 context の確認が止まった（exit 64〜66）、head ブランチが未コミットの変更や PR に無いコミットを抱えている（D-4）、必要なツールが無い
- 外部障害: GitHub の API・ネットワークの障害、CI 基盤の障害

次のものは結論 3 にしない: 未読・未検証、判断に迷う、修正が大きい、テストが失敗する（直す）、再現できない（根拠を付けて「解消済み」か「対応しない」にする）。

### D-14 記録: 完遂でも Spec を書いてコミットする

- 置き場所・命名・既存の文書の更新の規則は従来のまま。create-reso-world の `DOC_ROOT` の `docs/superpowers/specs/` に書き、同じテーマの既存の Spec があれば更新する。PR が create-reso-world のものなら `DOC_ROOT` は専用の worktree（PR の head）で、それ以外は文書用ブランチの checkout である
- 完遂では、承認待ちと確認用コピーを省く。Spec は 1 回だけコミットする。結論 1 では修正・検証・自己レビューの後（push の前）、結論 2 ではマージの前に、結果を書いて状態を `completed` にする。push・マージ・Issue 更新の結果は Spec に追記せず、状況コメントと完了報告に書く（記録だけのコミットを PR に足さないため）。結論 3 で止まったら `draft` のままコミットし、停止理由を書く
- 他のリポジトリの PR の Spec の公開は従来どおり。同じテーマの文書専用 PR があれば文書用ブランチを push し、無ければローカルのコミットだけにして「公開未実施」と報告する
- Spec の必須の中身に次を加える: 結論（三択のどれか）、D-7 の表、自己レビューの観点と結果（結論 1）、実行した検証と結果、実行許可（完遂の依頼の文言の要旨）。経路名は計画のみの流れでだけ書く

### D-15 PR の状況コメント

- 既存の `upsert_pr_comment.py` とマーカーを使う
- テンプレートの「作業判断」から「判断保留」の行を外す。「対応する」の行は「各 ID と、致命的である理由・確認方法を 1 行」にする
- 「作業結果」に「結論: 1 修正して push | 2 修正不要でマージ | 3 停止（理由）」と「自己レビュー: 観点と結果 | 未実施」を加える
- 投稿が必須なのは、従来の commit / push まで行ったターンと、結論 2（マージの前）である

### D-16 brainstorming を呼ぶのは計画のみの流れだけ
