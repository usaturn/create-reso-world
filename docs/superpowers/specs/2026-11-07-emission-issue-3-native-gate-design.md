## 目的

検証基盤の完成ではなく、利用者がアバターの発光を調整できることを最優先にする。まず「選択 → RGB編集 → 見た目が変わる → 元に戻す／OK」が1人で使える状態にする。

## A案（推奨）: 単独パネルを維持し、保証と検証を絞る

登録時だけPC側のResoLoopを使い、登録後の通常操作はResonite内で動く既存方式を維持する。既存のUI・RowPreview・RowCommand・Commit等を再利用し、新しい汎用制御基盤は作らない。

### 今回残す機能

1. 現在のワールドで明示したアバターを登録し、登録済み一覧から選択する。
2. 同じマテリアル参照を1行にまとめ、対象名・影響する既知のメッシュ・元値・RGB入力を表示する。
3. 有効なRGB入力をライブ反映する。HDR値を0..1に切り詰めず、Alphaと色プロファイルを保持する。不正値は書き込まない。
4. 編集開始時の完全な元値を1回保持する。「元に戻す」は復元して編集継続、キャンセルは復元して終了、OKは現在の変更を残して終了する。
5. 書き込みや復元が失敗した場合は、成功・復元完了と表示しない。

### 今回は保証しない・完了条件にしない

- 複数人の同時操作、操作者退出時の自動復旧、プレビュー途中での保存・再読込からの自動復旧。
- 登録後の構成変更、別ワールドへの登録情報の持ち運び、新しい共有先の自動発見、外部編集との完全な競合防止。
- 未登録ルートのドロップ、全幅・全表示条件の撮影、全材質型・全エラー経路の網羅。
- 外部共有先の完全なワールド走査と確認フロー。共有マテリアルはアバター外にも影響し得ることを表示し、確認できた共有先だけを表示する。未走査を「外部共有なし」と断定しない。

既存実装にある機能やガードは、削除するための作業をしない。上記は新規実装・追加検証・完成保証の対象から外すという意味である。通常利用を妨げる既存ガードは、具体的な原因を確認して必要箇所だけ簡素化する。

### 利用上の前提

1人で使い、同じ材質を別のツールやロジックと同時に編集しない。保存・移動・終了前にOKまたはキャンセルで編集を終える。構成変更や再接続で参照が失効したら再登録する。初回の実演は利用者データではなく、新しく作る試験用材質・メッシュで行う。

## 最低限残す確認

- 利用者指定の接続先と、操作する対象・フィールドを確認する。旧sessionのIDを推測して再生しない。
- 元値を保持し、変更先を選択対象のEmissionColorに限る。Rootや他人の物を削除しない。片付けは今回作成したと確認できる試験物だけにする。
- 変更後の対象値を一度読み戻し、実際の見た目と合わせて確認する。CLI exit0だけで動作成功としない。
- 原ファイル・過去のraw/Before/失敗記録は上書きしない。未確認の項目を確認済みと報告しない。

## 最小の受け入れ基準

動作環境は現在のDev Container、uv/Python、利用可能な現行ResoLoop/Flux/Resonite。接続先の申告は16070・前面であり、実行時に現在の接続を確認する。

新しい試験用対象1体・共有材1行から始め、日本語名、1を超えるRGB、Alpha非1の色を使う。単独操作で選択し、有効なRGB入力の見た目と読み戻し、元に戻す、キャンセル、OKを通して確認する。基本の不正入力1例が書き込まれないことも確認する。これが成立したら最小実用版として完了とし、二人操作・編集中の保存復旧・Drive失敗注入を待たない。複数行への拡張は、同じ実装を使う通常の確認にとどめる。
