## 1. 目的と実行許可

テストで守る挙動が無い変更にテストが作られ続ける状態を止める。全テストを採用基準で分類し、不要な検査を削除し、基準を計画とレビューで使う。

利用者はこのセッションで次を指示した。

- 進め方は「規則を先に決める」案（A）。PR は 1 本、コミットは領域ごと
- 「指示文は余計なことを書かずに担当が理解できる範囲で簡潔に記述すること。その他は途中で止めずに推奨案で進めて、PR まで作成して」

これは推奨案の選択、Spec・Plan の作成、実装、検証、作業ブランチへの push、PR 作成の実行許可である。未作成の文書を利用者が読んで承認したとは扱わず、Spec・Plan は draft でコミットして進める。マージは許可に含まれない。

## 2. 採用基準（`AGENTS.md`）

「基本方針」のテストに関する 3 項目を削除し、その直後に次の節を置く。基準はこの節だけに書く。

```markdown
## テストの採用基準

テストは、コードを実行して確かめる挙動があるときだけ書く。superpowers の TDD でも、守る挙動が無い変更ではテストを作らずに進める。

- 書く: コードを実行してロジック・分岐・安全条件・入出力の解析を確かめる場合、実際に起きた不具合の再発を防ぐ場合
- 書かない: 文書・SKILL.md の文面・設定値・一覧・雛形だけの変更
- 作らない型:
  1. 文書の文言を `in`／`not in` などで照合する
  2. 削除した旧ファイル・旧文言が無いことだけを確かめる
  3. ランチャー一覧・手順名・版・モデル名など、運用で変わる値をテストに写す
  4. スクリプトを実行せず、本文の文字列一致だけで判定する
  5. 同じ実体を複数のパス（symlink など）で検査する。pydantic・Pyright・ruff など他の仕組みが保証することを再検査する
- 安全な操作範囲・権限・凍結した履歴・利用者所有部分を守るための固定値は使ってよい。防ぐ誤りと理由をテストに書く
- テストを書かないときは、ツールの実行、静的解析・型検査、構造の検査（構文・参照先の実在）、`git diff` の確認で代え、結果を報告する
- Plan の各 Task に、テストの要否と理由を書く。不要なら、代わりの検証を検証手順にする
- レビューでは、追加・変更されたテストがこの基準に反していないか確かめる
```

`.pi/APPEND_SYSTEM.md` と `CLAUDE.md` は変えない（どちらのランタイムも `AGENTS.md` を読む）。

## 4. 棚卸しと削除

### 対象

Issue の範囲（138 ファイル、基準 HEAD の静的集計）と、その fixture・helper・probe・runner・テスト設定。#49・#50 は PR が無いので対象外。着手時に open PR を再確認する。

### 分類

各ファイルを「削除」「統合」「書き換え」「理由付き固定値として維持」「維持」に分ける。混在するファイルは関数または assertion 単位で分ける。判断は第 2 章の基準と Issue の「原則として削除・統合するもの」「残すもの」による。

- 既存の「消えたことの検査」は原則削除する。誤操作・無効設定の再導入を今も防いでいるものだけ、理由を書いて残す
- 実行するコードのテストを消すときは、同じ経路と重要な失敗条件を守る残りの検査を挙げる。消す検査だけが持つ有効なケースは統合する
- 書き換えは価値がある場合だけ行う。別の語句一覧・件数固定・弱い assertion・新しい汎用パーサで置き換えない
- 参照が無くなった fixture・helper・import・runner の呼出しも消す。空の wrapper や実行されない suite を残さない
- ワールドで具体的な数値を使っているだけでは削除しない。生成処理を実行して配置・重なり・所有範囲などを検査するものは残す

### 分類表

`docs/superpowers/specs/2026-10-07-issue-51-test-inventory.md` に領域ごとに書く。列は「場所」「検出する不具合」「判断」「理由」「代わりの保証」「関連」。前後比較もこのファイルに書く。

### 新しいテストを作らない

この作業はテストの削除・統合・書き換えだけで、新しいテストファイルは作らない。書き換えた検査は、隔離したコピーで「許容すべき変更で成功する」「検出対象の誤りで失敗する」を確かめる。期待値を変異に合わせて直さない。
