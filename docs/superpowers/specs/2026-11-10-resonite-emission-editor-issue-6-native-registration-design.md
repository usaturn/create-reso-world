## 目的

未登録の初期パネルをインベントリへ保存し、取り出した同じパネルへ、Resonite 内のドロップ操作だけで対象アバターの材質を登録して発光編集できるようにする。登録時も通常の編集時も、PC 側の ResoLoop・Python・外部常駐プロセスを必要としない。開発時の初回生成・配備に ResoLoop を使うことは、この目的と区別する。

## 調査結果（2026-11-10、実測）

- 実行環境: Resonite managed data `2026.11.6.1136`、Flux-SDK `1.9.0`、ResoLoop `0.2.0`。Froox ノード 3321 件を `resoloop flux node search`／`describe` で確認した。
- Slot から任意の Component を取得するノード（`GetComponent`、`GetComponentsInChildren` など）は存在しない。`GetComponent<MeshRenderer>` を呼ぶ .pg は「module として構築できない」、`GetComponentsInChildren` も同様にコンパイルできなかった。
- Resonite Wiki の「Component / With ProtoFlux」は、ProtoFlux が Component を動的に生成・削除・探索できないと明記している。該当する Resonite Issue #57 は 2026-11-10 時点でも open である。Wiki が危険とする Ref Hacking は使わない。
- `UIX.ReferenceReceiver<T>` は、ユーザーが UIX 要素へドロップした参照を `ISyncRef<T>` の対象へ保存する。Wiki は、Slot・音楽・value field の参照をパネルへ受け取る用途を挙げている。
- `as<FrooxEngine.IValue<colorX>>(Dropped)`、`ValueSource<colorX>`、`FieldAsVariable<colorX>`、`FireOnObjectValueChange<IWorldElement>` を使う .pg は Flux-SDK 1.9.0 でコンパイルできた。
- 以上の結果、当初案の「Root を 1 回ドロップすると native が配下の Renderer と材質を自動列挙する」方式は、現行の ProtoFlux では実現できない。PC 補助や動かない空パネルへの置き換えは、利用者の選択を得て行う。

## 利用者の決定

2026-11-10、調査結果と次の選択肢を示し、利用者が「native 多段ドロップへ変更（推奨）」を選んだ。

- 保存版パネルに固定行プールを用意する。
- アバター Root のドロップに加えて、各材質の `EmissionColor` フィールドを利用者が行へドロップして登録する。
- native だけで完結する。
- 次の制約を受け入れる。Root 1 回の自動列挙、メッシュ影響一覧、参照 ID による材質の重複排除、材質名の取得はできない。行数上限と操作手順が変わる。実機での受信可否確認が必要になる。

## 方式

### パネル

固定 16 行の行プールを持つ、独立した平面パネルを新しく生成する。

- 全体: 見出し、説明、状態表示、アバター Root のドロップ領域、「編集を開始」、OK／元に戻す／キャンセル。
- 各行: 行番号と登録状態、材質フィールドのドロップ領域、元値／現在値、RGB 入力、行の選択ボタン、行の状態。
- 各行のドロップ領域は `UIX.ReferenceReceiver<FrooxEngine.IWorldElement>` を使い、行ごとの `ReferenceField<FrooxEngine.IWorldElement>` に参照を保存する。ドロップは参照を保存するだけで、材質の色・構成・親・メッシュを変更しない。
- アバター Root は既存と同じ `ReferenceReceiver<FrooxEngine.Slot>` で受け、表示名の確認と編集開始の条件に使う。
- 初期状態は、16 行すべての参照が null、アバター 0、材質 0、未選択、操作者未取得、プレビュー記録なし、試験用 fixture なし、外部参照なしとする。パネルの所有キーは `emission-registrable-panel-<token>`、ルート名は `ResoLoop_Test_EmissionEditor_Registrable_<token>` とする。

### 登録と編集の流れ

1. パネルをインベントリから取り出す。必要なら「編集を開始」で操作者を取得する。操作者を取得した状態を初期保存版に残さないため、保存は開始前に行うよう案内する。
2. 対象アバターの Root をアバタードロップ領域へドロップする。Slot の表示名を状態欄に出す。名前が `Root` の Slot は拒否する。`AvatarRoot` Component の有無は native では検査できないため、利用者が対象を確認する。
3. 編集したい材質の `EmissionColor` フィールドを、行のドロップ領域へ 1 つずつドロップする。値フィールドの参照を受け取るだけで、色は変更しない。
4. 行の選択ボタンを押すと、その行の元値・入力欄・状態を捕捉し、既存と同じ RGB ライブ編集、元に戻す、キャンセル、OK が使える。
5. 行を切り替えるには、プレビュー中でないことを条件にする。プレビュー中は既存と同じ拒否メッセージを出す。
6. 編集中の記録がある行は、その行のドロップ受付を無効にする。記録を閉じるまで、行の参照を別のフィールドへ変えられない。
7. 重複するフィールド参照、`colorX` でない参照、登録のない行は選択できない。重複は行ごとに表示し、別のフィールドをドロップして解消する。

### 行の状態と保護

- 選択時に、ドロップされたフィールド参照を `CapturedField` として行へ保存する。以後の読み取り・プレビュー・復元は `CapturedField` だけを対象にする。記録がある行はドロップ受付を無効にするため、編集中に参照が変わることはない。記録を閉じた後の再選択では、その時点のドロップ参照を新しい `CapturedField` として捕捉する。
- プレビューは既存の RowPreview の手順を保つ。書き込み前の記録、`FieldAsVariable` による1回の書き込み、5 成分（R/G/B/A/Profile）の読み戻し、競合検出、不正入力の拒否を残す。
- 元に戻す・キャンセル・OK は既存の RowCommand／Commit の意味を保つ。元に戻すは元の完全な色へ復元して編集を継続し、キャンセルは復元して終了し、OK は変更を保持して終了する。復元・書き込みの失敗を成功と表示しない。
- 既知の利用先ガード（登録した Renderer の Materials リストと index の照合）は、Renderer を列挙できないため使えない。代わりに、`CapturedField` が非 null であること、行の登録参照と一致することを書き込み前に確認する。
- 材質名、影響するメッシュ、参照 ID 単位の重複、外部共有先は取得できない。パネルには「共有材質はアバター外にも影響する場合があります（共有先は未走査）」と表示する。`EmissionColor` 以外の `colorX` フィールドをドロップした場合、native ではフィールド名を検査できない。利用者が正しいフィールドを選ぶ責任を負うことを表示する。
- 登録処理は材質へ書き込まない。書き込みは行の選択後のプレビュー・復元・OK の経路だけである。

### 上限と再登録

- 行数は 16 で固定する。1 行につき 1 フィールド、同じフィールドは 1 行だけ登録できる。17 個目以降は行がないため登録できない。これは黙って切り捨てず、画面の行数上限として明示する。16 行はすべて画面に表示し、空の行もドロップ先として使える。
- 別のフィールドへ変えたいときは、その行へ新しいフィールドをドロップし直す。記録の残っている行はドロップ受付を無効にし、復元・キャンセル・OK で記録を閉じるまで `CapturedField` を使い続ける。
- 行の登録を空へ戻す専用操作は設けない。不要な行は未登録のままにするか、別のフィールドで上書きする。
- 別のアバターへ切り替えるときは、Root をドロップし直し、必要なら行を新しい材質で上書きする。編集中の記録は `CapturedField` に残るため、Root の変更で復元対象を失わない。

### 保存・複製・別ワールド

- パネルの状態はすべてパネル配下のフィールドに置く。固定の過去 session、過去の generation、外部 ID に依存しない。初期保存版には外部参照を含めない。
- 保存・複製したパネルは、それぞれの行の `ReferenceField` と状態を独立して持つ。別のパネルの内部状態へは接続しない。
- 登録済みのパネルは、ドロップしたフィールドへの外部参照を持つ。同じワールドで保存・再読込した場合はその参照を使えるが、別ワールドへ持ち込んだ場合は参照先が失効し得る。その場合は Root とフィールドをドロップし直す。
- 同じ材質を 2 つのパネルで同時に編集する場合の競合防止は、既存と同じく行ごとの外部変更検出に限る。多人数同時編集の保証はしない。

## 受け入れ基準

1. 初期保存版は、アバター 0・材質 0・未選択・操作者未取得で、アバター／User／試験 fixture への外部参照やプレビュー記録を含まない。
2. 初期版をインベントリへ保存して取り出したインスタンスで、PC 補助を起動せずに、Root と材質フィールドをドロップして登録できる。
3. `colorX` の値フィールドだけを受け付け、`colorX` でない参照と重複参照は明示して拒否する。16 行を超える登録はできないことを表示する。
4. 登録処理だけではアバターの色・材質構成・親・メッシュを変更しない。
5. 登録後、既存と同じ RGB ライブ編集・元に戻す・キャンセル・OK が使え、HDR RGB・Alpha・profile と元の完全色を保持する。
6. 未登録・プレビュー中・復元待ち・失敗時に編集を有効化せず、登録や復元の失敗を成功と表示しない。
7. 保存・複製後のパネルが別のパネルの内部状態へ誤接続しない。固定された過去 session や外部 ID がなければ動かない保存物にしない。
8. 別ワールドでの確認範囲、行数上限、再登録の扱い、自動列挙できない情報を Spec に明記する。元値や未確定プレビューを黙って捨てない。
9. 実機では、新規の試験用対象で登録・編集・復元を確認してから、利用者が明示した実アバターで最小の通常操作と読み戻しを確認する。実機確認はマージ後に利用者の操作を伴う。
10. 最後に、利用者が保存できる未登録の初期パネルを Resonite へ新規配備し、対象を画面上の名前で案内する。既存パネルと実アバターは保持する。この配備と案内はマージ後に実施する。

## 対象外

- 任意 Component の動的列挙、材質名・影響メッシュ・外部共有先の自動取得、参照 ID 単位の材質重複排除。
- PC 側 ResoLoop を登録に使う方式への置き換え。
- Ref Hacking、未検証の内部 API、カスタム mod／DLL の導入。
- 多人数同時編集、編集中の保存・退出からの完全復旧、全材質型・全表示条件の保証。
- 既存の完了済み Spec・Plan を pending へ戻すこと。既存のガードを削るためのリファクタ。
- Actions の有効化、release、branch／worktree の削除。

## 検証方針

- 文書・設定の変更はテストしない（F/L）。Spec と Plan の整合は読み合わせと `git diff` で確認する。
- Python の生成物は、初期パネルに外部参照がないこと、行ごとのモジュールがその行のフィールドだけを参照すること、行数上限を超えないことを、実行して確かめる。壊れると誤対象への書き込み・元値喪失・別パネルへの誤接続になるものだけを S としてテストする。
- .pg は `flux-sdk build` で全ファイルをコンパイルし、manifest は `resoloop flux validate-manifest` で確かめる。実機の動作確認とは区別する。
- 既存の suite（`uv run pytest`）を通す。テストの採否は create-reso-world の「テストの採用基準」に従う。
