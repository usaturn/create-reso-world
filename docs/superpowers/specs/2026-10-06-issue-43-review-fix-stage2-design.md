## 1. 目的

#38 で `review-fix-planning` は、修正要否を三択（1 修正して push／2 修正不要でマージ／3 停止）で確定して完了まで進めるスキルになった。#5 の対応方針 A のうち、次の 3 点が残っている。

1. **経路を上げる条件**: 同じ仕組みを続けて直した、または修正が回帰を生んだときに、点の修正をやめて設計の見直しに切り替える条件と、切り替えた後の動き
2. **失敗時の検証の方針**（#5 のコメント「PR #27 の調査結果」の P2・P3）: 失敗時に管理する状態全体が変わらないことを確かめる、負例には異常を 1 つだけ入れる、ガードを外した対照で検出力を確かめる
3. **同じ原因が再び出たときの再判断と、公開の単位**（同じコメントの P5）

この 3 点を `review-fix-planning` に入れる。

## 2. 背景

- usaturn/resoloop#5 では、レビュー修正 13 コミットのうち 9 件が同じ関心事（再読込後の key と Component の対応）を直し、うち 4 件は直前の修正が入れた回帰、3 件は直前の修正の適用漏れだった。9 ラウンドすべてを bounded と判定し、同じ仕組みを何度直しても経路が上がらなかった（#5 の本文「根本原因 2」）
- PR #27 では、拒否のテストが終了コードと対象のファイルだけを比べており、バックアップや認証が先に変わる実装でも成功した。2 つの異常を含む負例は、確かめたいガードを外しても別の拒否の理由で止まり、欠落を検出しなかった（同コメントの 2 章 B・D）
- #38 は、修正後の自己レビューを 1 回までにし、致命的な指摘だけを直す形にした。一方で、同じ条件が再び破れたときの扱いと、失敗時の検証の中身は決めていない（#38 の Spec の 7 章）

## 3. 決定事項

### D-1 経路の引き上げと三択の方針の関係（利用者の判断が要る点）

#43 の「設計で利用者の判断が要る点」の選択肢と、エージェントの推奨は次のとおり。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| (a) | 結論 3 の理由に「同じ問題群の再発」を加えて止める | #5 の A の例と分割 Spec の 10.3 と同じ形。利用者が「既知の制限」「分割」「再設計」を選べる | #38 の D-2・D-13（止まるのは権限・環境・外部障害だけ）とぶつかる。再発のたびに判断が利用者へ戻る |
| (b) | 止めずに、設計の見直し（守る条件の文書化と影響経路の全面的な見直し）を修正の中で行う | #38 の「完遂」「設計の選択も推奨案で進める」（D-9）と矛盾しない。#5 の根本原因 2（条件を文書にしないまま点の修正を繰り返した）を直接ふさぐ | 大きな見直しが利用者の確認なしに既存 PR へ push される |
| (c) | 計画のみの流れに切り替え、Spec を書いて承認を待つ | 大きな見直しの前に利用者の確認が入る | (a) と同じく止まる。#38 の完遂の方針とぶつかる |

**推奨は (b)。** 理由は次のとおり。

- #38 で利用者は、権限・環境・外部障害の場合を除き止まらないこと、設計の選択でも推奨案を選ぶことを決めている。(a)・(c) はこの決定を、再発の場合に限って覆す
- 循環を止める仕組みは #38 で既にある（致命的な指摘だけを直す、自己レビューは 1 回まで）。足りないのは、再発したときに直し方そのものを変える手順であり、止めることではない
- (b) の短所は、push してもマージはしないこと（結論 1 はマージしない）、見直しの内容を Spec と状況コメントに残すこと、次のレビューがそれを読むことで抑えられる

**採用: (b)。** 利用者は 2026-10-06 に「推奨案で進めて、途中で止めずに PR まで作成せよ」と指示した。選択肢を個別に見たうえでの選択ではないが、推奨案の採用を明示した指示なので、この指示を利用者の選択として扱う。利用者は PR のレビューで (a)・(c) に変えられる。その場合は、この Spec の D-1・D-3 と SKILL.md の該当する節を直す。

### D-2 きっかけ（観察できる条件）

「対応する」項目ごとに、守る条件と影響経路の表を作るときに、次のどれかに当たるかを確かめる。

1. **同じ守る条件の 2 回目**: 破れている条件、または直す仕組み（関数・state の項目・判定）が、同じ PR の以前の回で致命的な指摘として直したものと同じである。前の回の表で漏れた隣の経路（適用漏れ）も含む
2. **修正が生んだ回帰**: 指摘の原因が、同じ PR の以前のレビュー修正のコミットが入れた変更である
3. **自己レビューでの再発**: 修正後の自己レビューで、この回に直した条件がまた破れている、またはこの回の修正が原因の致命的な指摘が出た

- 以前の回は、同じテーマの Spec の記録（以前の回の表と結論）と、PR のコミット履歴（`git log`）で確かめる。回帰は `git log -L`・`git blame`、またはそのコミットの前後での再現で確かめる
- 以前のレビュー修正が PR の履歴にも Spec にも無ければ、1・2 には当たらない
- 数えるのは「対応する」項目だけである。致命的でない指摘（「対応しない」）は数えない。分割 Spec の 10.3 が「どの問題群にも入らず、不変条件も破らない指摘は数えない」としたのと同じ考え方で、直さないものは循環を生まない

### D-3 切り替えた後の動き（完遂）

結論 3 にはせず、結論 1 の修正の中で次を行う。

1. **守る条件を文書にする**: Spec に「守る条件の設計」を書く。条件を、再現した 1 経路ではなく、その仕組みが扱うすべての状態・操作順・停止位置で成り立つ性質として書く。条件を保つ仕組み、以前の回の修正（コミット）と、それぞれで足りなかった理由も書く
2. **影響経路を全面的に見直す**: 表を、今回の指摘の経路からではなく、仕組みから作り直す。その state の項目を書くすべての箇所、その関数のすべての呼出元、すべての停止・失敗の位置を列挙する。各行に、変更前の挙動と、確かめる assertion（何を比べるか）を書く。#38 の表に無かった「呼出元の旧挙動」「対応する assertion」の列は、ここでだけ求める（通常の修正の表は変えない）
3. **直し方を選び直す**: 少なくとも「点の修正を続ける」「条件を 1 か所で保つ形にまとめる」「PR の保証を狭めて条件を不要にする」を比べ、推奨案を選ぶ。条件が構造で成り立つ案を優先する。点の修正を続けるなら、列挙したすべての経路で条件が成り立つ根拠を書く。保証を狭めたら、PR の説明の保証と既知の制限を直す。PR の分割は第二の PR になるので行わない（スキルの「第二の PR を開かない」）。分割がより良いと考えたら、他の案として Spec に残す
4. **全経路で確かめる**: 検証を、再現した場面だけでなく、列挙したすべての経路で条件を確かめる形にする。失敗時の扱いなら D-5 に従う
5. 結論 1 の残りの手順に戻る。自己レビューの反証の担当には、守る条件の設計も渡す

きっかけ 3 で切り替えたときも、自己レビューの 2 回目はしない（#38 の D-10）。見直した内容は再レビューしていないことを Spec と状況コメントに書き、次のレビューで重点的に見てもらう。

### D-4 切り替えた後の動き（計画のみ）

計画のみの流れでは、brainstorming に経路を判定させるときに、当たったきっかけと根拠を渡し、architectural にさせる。brainstorming の「隠れた複雑さが見つかったら経路を上げる」を、観察できる条件で適用する形である。Spec には D-3 の 1〜3 を書いて承認を求める。

### D-5 失敗時の検証

「対応する」項目の守る条件が、失敗・拒否・中断したときの扱い（「不正な入力なら何も変えずに止まる」「途中で止まっても中途半端な状態が残らない」など）であるとき、その修正の検証を次の形にする。

1. **状態全体を比べる**: 失敗させる前と後で、その処理が管理する状態全体を比べる。対象のファイルに加え、共有先（symlink の参照先、hard link の相手）、バックアップ、認証、一時ファイル、キャッシュ、外部コマンドの呼出しを含める。ファイルは有無・バイト列・mode・リンクの種類と参照先を見る。期待値は失敗させる前の状態から取り、固定値を書かない
2. **副作用の順序を確かめる**: 入力の不正で止める処理は、どの状態を変えるよりも前に、すべての入力（構文・値・必要な内部構造・保存先の種類）を検査しているかを確かめる。書き込みの途中の I/O の失敗は入力の不正と分け、何が残り、どこまで戻すかを Spec に書いて確かめる
3. **負例には異常を 1 つだけ入れる**: 他の条件は正常にし、想定した理由で拒否されたことと、状態が変わっていないことを確かめる
4. **ガードを外した対照で検出力を確かめる**: 修正の中心になるガードを 1 つだけ外した版で、そのガードを確かめるすべての負例が失敗することを確かめる。ガードを外すのは、隔離 worktree（手順 3 と同じ `mktemp` の方法）に修正後の内容を写したものだけで、専用の worktree では外さない。終わったら手順 3 の teardown と同じ方法で消す。安全に関わる境界に絞り、すべてのコードの変異テストは求めない

- テストを足すのは、致命的な指摘の修正と検証に要るときだけである（#38 の D-6 と「分類の仕様」）。D-5 はテストの書き方の方針で、テストを足す理由ではない
- 1 の期待値は実行の前の状態から取るので、固定値のテストにならない（`AGENTS.md` の基本方針、#36）
- 修正後の自己レビューの観点 3（検証の検出力）は、この 4 点で見る
- 結果（比べた状態、対照で失敗した負例の数）を Spec に書く

### D-6 公開の単位

結論 1 の push の前に、次がすべて済んでいることを確かめる段を足す。途中の修正を先に push しない（P5 の「個別パッチを即 push しない」）。

- 関連テストと変更の種類に応じた検証が、最後の修正の後に通っている
- 自己レビューの全指摘に判定がある（直した、または「対応しない」と理由）。未確認の事項は、未確認として Spec と状況コメントに書く（#5 のコメントの「独立レビューの反証候補を完了判定へ引き継ぐ」の要点）
- Spec と PR の説明に書いた件数・参照先・保証が、実装と検証の結果に合っている
- 公開済みのコミットを書き換えない（force push しない）。push 前のローカルのコミットは途中の区切りとして残してよい

### D-7 結論 3 の理由にしない

「同じ条件の再発」を、結論 3 の理由にならないものの一覧に加える（D-1 の (b)）。

### D-8 記録

- Spec の必須の中身に、きっかけに当たった項目の「きっかけと根拠」「守る条件の設計」「比べた直し方と選んだ理由」と、D-5 を行ったときの「比べた状態と対照の結果」を加える
- 状況コメントのテンプレートの「作業判断」に「設計の見直し: なし | 項目の ID、きっかけ、選んだ直し方」の行を足す。3 つの見出しとその順序は変えない

### D-9 合理化の表と Red flags

次の言い訳と、その実態を足す。

| 言い訳 | 実態 |
| --- | --- |
| 前の回と同じ条件だが、今回の経路は別なので点の修正で足りる | 同じ守る条件の 2 回目である。設計の見直しに切り替え、仕組みから経路を列挙し直す |
| 回帰は、入れたコミットを直せば済む | 修正が生んだ回帰は、前の回の列挙が足りなかった証拠である。設計の見直しに切り替える |
| 同じ問題が続いたので、止めて利用者に判断を仰ぐ（完遂） | 完遂では止まらない。設計の見直しを修正の中で行う |
| 拒否のテストは非ゼロ終了を確かめているので十分 | 状態全体を比べる。対象のファイルが変わらなくても、バックアップや認証が先に変わることがある |
| 異常を詰め込んだ負例 1 本で網羅できる | 別の拒否の理由で止まり、ガードの欠落を見逃す。負例には異常を 1 つだけ入れる |
| ガードを入れたのでテストも効いているはず | ガードを外した対照で、負例が失敗することを確かめる |
| 直した分だけ先に push しておく | 検証・自己レビューの判定・記録の確認が揃うまで push しない |

Red flags に次を足す。

- きっかけに当たるのに、守る条件の設計を書かずに点の修正をしようとしている
- 同じ条件の再発を理由に結論 3 で止まろうとしている
- 失敗時の扱いを直したのに、検証が終了コード・メッセージ・対象の 1 ファイルしか見ていない
- 1 つの負例に異常を 2 つ以上入れている
- ガードを外した対照を専用の worktree で行おうとしている
- 自己レビューの指摘の判定や記録の確認が済む前に push しようとしている

## 7. リスク

- **設計の見直しが大きくなる**: (b) では、利用者の確認なしに大きな直し方の変更が既存 PR に push され得る。結論 1 はマージしないこと、見直しの内容と比べた案を Spec と状況コメントに残すこと、次のレビューが読むことで抑える。利用者が (a)・(c) を選び直せば、D-1 に戻って直す
- **きっかけの判定が記録に頼る**: 以前の回の表が Spec に無いと、きっかけ 1 を見落とす。PR のコミット履歴でも確かめる形にし、#38 以降は表が必須なので記録は揃っていく
- **SKILL.md の肥大化**: 既に約 33KB ある。新しい節は要点に絞り、既存の節（隔離 worktree、teardown、自己レビュー）は参照で再利用する
- **失敗時の検証の重さ**: 対照の実行は手間がかかる。安全に関わる境界のガードに絞り、変異テスト一般は求めない
